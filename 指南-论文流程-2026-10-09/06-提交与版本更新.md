# 06 提交与版本更新

## 本轮需要交什么

先记录学生选择的动作与本轮沟通目的，再结合论文阶段确定材料范围；目的不明确时停在“待学生决定”。AI 先只读盘点，正式复制和加工放在学生决定之后。

第 1—5 阶段的新模板已确认；通用指导内容仍处于本地开发，模板确认不代表已经发布。旧文件编号不代表新阶段编号。导师已明确要求的材料不能自行省略。

| 交流任务 | 当前交付约定 |
|---|---|
| 创新点与实验设计讨论 | 一份完整讨论文档，参考文献和图表集中其中 |
| 实验进展与结果汇报 | 按已确认的五部分模板整理一份 Word（`.docx`），图片嵌入正文，不提交 PDF |
| 初稿审阅 | 论文资源文件夹：Markdown 审阅说明与正文，独立图片和相关代码；不交 Word 或 PDF |
| 导师意见修改复核（仍属第 3 阶段） | 同上，将逐条修改情况并入审阅说明；核对前后版本与原意见，不额外要求独立修改说明 |
| 投稿前确认 | 论文资源文件夹：00-投稿确认.md、01-论文正文.md、独立图片和相关代码；不交 Word 或 PDF |
| 收到审稿意见后讨论修改方案（第 5 阶段） | 论文资源文件夹：00-审稿处理说明.md、02-审稿意见.md、对应版本的 Markdown 正文、独立图片和相关代码；03-逐条回复.md 可暂不提供，不交 Word 或 PDF |
| 修改完成后核对稿件与回复（第 5 阶段） | 同上，并提交 03-逐条回复.md 与对应修订稿；核对实际修改、回复、位置和证据 |

第 1、2 阶段不另行强制提交说明、清单、PDF 或附件；选填栏目可省略，尚未完成或不能确定的内容如实说明，可写“待讨论”并列出具体疑问。第 2 阶段每项实验的必要条件、结果图表与分析放在一起；没有得到预期结果或尚无完整结果，也可汇报。其他专题请教仍按本轮目的选择必要内容，不因论文阶段强制交整篇。

各阶段的提交清单、自查、来源、人工确认、打包和发送记录留在本地，可直接记在任务状态，不必另建文件或随材料提交；[提交清单模板](../模板-学生材料-2026-10-09/06-提交清单模板.md) 供核对参考。第 3—5 阶段正文用相对路径引用图片，代码 README 说明用途、对应图表或结果、运行方式和数据位置；没有相关代码时注明不适用。任务状态默认留本地，导师明确需要时只提供人工确认时副本。

第 4 阶段的投稿确认说明包括投稿目标、稿件状态、投稿要求核对、作者与相关信息、请导师确认五部分。写清拟投稿版本、较上轮变化及未解决问题，记录目标期刊或会议的官方要求链接和查阅日期，核对篇幅、格式、匿名、图表和附件要求，以及作者姓名、顺序、单位、通讯作者和适用声明。备选目标及理由、预计投稿时间为选填。每项按实际依据标明“已核查／待核查／发现问题／不适用”，不确定的内容保留待确认。

第 5 阶段分为“收到意见后讨论修改方案”和“修改完成后核对稿件与回复”两个环节，见[审稿与审稿回复指南](07-审稿与审稿回复.md)。[审稿处理说明](../模板-学生材料-2026-10-09/07-审稿处理说明模板.md)写明投稿目标、稿件编号、审稿轮次、对应稿件版本、编辑决定、返修期限（如有）、本轮沟通目的及请导师判断的问题；讨论方案时逐条填写意见理解、拟采取的动作、优先顺序与理由，无须先完成修订。[审稿意见](../模板-学生材料-2026-10-09/08-审稿意见模板.md)完整保留编辑及各审稿人的意见原文和编号；中文翻译选填，不能以摘要或翻译替代原文。

修改完成后按[逐条回复模板](../模板-学生材料-2026-10-09/09-逐条回复模板.md)整理：原意见编号及原文、拟提交的正式回复、实际修改位置与支撑依据、尚未解决事项及原因（没有则写“无”）。回复所称修改须能在材料中找到，计划开展的工作不能写成已经完成。讨论方案时可暂不提供逐条回复。

给导师审阅使用上述资源文件夹；实际投稿或返修上传文件按目标刊会要求另行准备，与导师确认的内容保持一致。完成本轮材料不表示已经生成期刊上传文件，也不表示已经投稿或返修提交。

## 整理文件与版本

一份提交包只对应一篇论文的一个版本。首次交付可用 v01，后续依次 v02、v03；这与指导包版本 0.4.0 是两套编号。Git 拉取更新的是通用指导包，个人交付材料仍按本地版本留档和备份。

第 3—5 阶段以资源文件夹名称标明论文、版本和日期，内部文件名保持稳定。以下为第 3 阶段示例；第 4 阶段在新版本目录中沿用资源结构，入口改为 00-投稿确认.md；第 5 阶段入口改为 00-审稿处理说明.md，并按本轮环节加入审稿意见及逐条回复：

```text
提交包-P001-v02-2026-10-09/
├─ 00-审阅说明.md
├─ 01-论文正文.md
├─ 图片-论文图表-2026-10-09/
└─ 代码-论文相关-2026-10-09/
   ├─ README.md
   └─ 相关代码及配置文件
```

以上均为命名示例，不代表已存在的文件；日期使用实际创建日期。尚无正式编号时用论文短标题代替；不要使用“最新版”“最终版2”等难以区分的名称。其他阶段独立文件可使用“论文编号-材料名称-v版本-YYYY-MM-DD.扩展名”。另有必要证据时，在相应材料中列清用途。

提交包目录在人工确认前作为本轮材料整理区，确认后才能生成正式压缩包。只复制本轮所需文件，并记录来源、版本与用途；原工程和原始审稿反馈保留，不移动、不删除、不自动回写。补研究或修改原工程需另行明确任务。

后续交付另建版本目录，不覆盖已提交版本。材料中的路径以提交包为起点；本地任务状态记录原工程位置及版本，避免导师收到的材料只写自己电脑上的绝对路径。

## 本地版本记录与持续维护

- 使用版本号和日期区分各轮交付，在已有任务状态的版本记录中写明：依据的导师反馈、本轮主要变化、对应稿件或工程版本、提交状态。
- 工程版本使用能够追溯的现有版本号或研究记录标识；暂时无法确认就写“待核对”，不要自行编造。
- 收到导师、编辑或审稿人意见后保存原反馈，更新当前进度、修改安排和下一步；形成新版交付后补记版本记录。
- 已提交材料保留原样；新一轮在新版本目录中整理。定期备份交付文件夹，包括历轮稿件、导师及审稿意见和版本记录。

## AI 自查

1. 材料回答了学生本轮希望导师判断的问题，范围与学生选择一致。
2. 主文件和版本明确，说明与资源能对应；第 3—5 阶段核对图片相对路径、图号及代码与结果的对应关系，其他任务按适用要求核对文件。
3. 模板提示已妥善处理，选填栏目可省略，尚未完成或不能确定的内容如实说明；第 3 阶段首次提交省略修改情况，按导师意见再次提交时逐条填写。第 4 阶段核对官方要求链接、查阅日期及各项状态的依据，未核查不能记为符合要求。第 5 阶段核对原意见完整性、编号和对应轮次；讨论方案时不要求先完成修订或正式回复。
4. 每项“已完成”和重要结论有对应材料，修改有位置；第 5 阶段修改完成后的核对环节，检查回复与实际改动及证据，未验证内容、缺失证据和待讨论问题如实列出，计划不能写成已完成。
5. 本轮材料能够对应来源与版本，不混入无关旧稿、缓存、账号信息或整份工程。

自查记录写明实际检查范围、发现的问题和未核实事项。AI 自查不等于复现实验或科研结论已验证。需要修订的内容先处理，再将实际文件和清单交学生审核，状态记为“待人工审核”。

研究问题尚未解决，可以诚实提交当前进展请导师判断；缺少证据不能写成验证通过。必要材料缺失时明确说明影响和补交安排，供学生决定是否按当前范围沟通。

## 学生人工审核

学生查看本轮实际材料以及本地文件清单，确认事实、表达及沟通目的；第 1 阶段核对讨论文档，第 2 阶段核对 Word 及内嵌图片，第 3—5 阶段核对 Markdown 正文、独立图片、代码与对应说明，第 5 阶段另核对原意见及本轮方案或回复。AI 自查后的摘要不能代替实际文件；未实际运行代码时不得记为已复现结果。

学生要求修改时，返回“整理中”，修改后再次自查和人工审核。学生明确确认具体版本及文件清单后，才记为“待打包”；确认记录放在本地任务状态中。学生确认可打包并发送给导师，不等于导师已同意该投稿目标、稿件版本、修改方案或向期刊投稿、返修提交。

## 按确认版本打包

1. 按人工确认的清单，将同一版本的文件生成交付包，保留目录和相对路径；不临时改写正文、替换图片或代码、增减附件。第 3—5 阶段不额外生成 Word 或 PDF。
2. 检查压缩包可打开、文件齐全且内容与确认版本一致；如发现需改内容或清单，回到整理与审核。
3. 核对完成后，在本地任务状态记录包名、对应版本和核对结果，状态转为“待发送”。不向已确认的包内文件追加打包或发送记录。

本地任务状态若被要求随包提交，包内只放人工确认时的副本。正式压缩包不包含无关历史、通用指导包或整个研究工程。

流程状态：**待学生决定 → 整理中 → 待人工审核 → 待打包 → 待发送 → 已提交**。其中“已提交”只根据学生实际发送的信息填写，不等于导师已接受。

## 从哪里提交

**提交渠道：待导师指定。** 由学生通过指定邮箱、教学平台或共享目录发送；AI 不自动代发。学生反馈实际发送信息后，在本地任务状态记录时间、版本、去向及“已提交”状态。

GitHub 不收学生交付物，不要求学生建仓库、push、提 PR 或发 Issue。投稿前检查或返修材料准备完成，不等于已经获准向期刊或会议投稿、返修提交；按导师确认的安排执行。

## 更新指导包

指导包版本见根目录 VERSION，具体变化见 [更新记录](../CHANGELOG.md)。通用指南目录名称中的日期是建立日期，不因每次内容更新而改名。

### 主要方式：拉取更新

1. 先备份论文交付子文件夹，保留已提交版本。通用指南和空白模板平时保持原样，模板复制后填写。
2. 在克隆的指导包仓库根目录打开终端，确认是导师提供的仓库及约定分支，查看本地状态：

```text
git status
```

3. 确认通用文件没有本地改动后，执行：

```text
git pull --ff-only
```

该命令仅在能够直接接续远程历史时更新；遇到本地分叉会失败。[Git 官方说明](https://git-scm.com/docs/git-pull)

如发现本地修改、分支不符或更新失败，先保留现状并说明原因，再处理；不要强制覆盖、丢弃修改或清理个人材料。模板中误填的内容也应先保留。

4. 更新成功后阅读 CHANGELOG.md 和 VERSION，按需调整当前材料，在任务状态中记录正在使用的指导包版本。论文交付 v01、v02 等继续独立编号；历史已提交材料保留当时使用的指导包版本，不批量重写。

指导包的 Git 历史不记录被忽略的个人交付材料，拉取更新也不等于已经备份这些材料。原研究工程继续保留原位。

### 备用方式：ZIP

1. 下载新版本 ZIP，先解压到独立位置，阅读更新记录，并备份现有交付材料。
2. 只替换旧副本中的 README.md、AGENTS.md、VERSION、CHANGELOG.md、.gitignore，以及“指南”“模板”“示例”三个通用目录；保留论文交付子文件夹和已填材料。
3. 按需调整当前材料并更新任务状态中的指导包版本；不要用空白模板覆盖已填文件，也不改写历史已提交版本。

ZIP 解压目录不能直接使用 Git 拉取更新。以后改用 Git 时，先在独立位置克隆仓库，再复制并核对个人交付文件夹，保留旧副本。

如果新旧规则影响正在进行的导师任务，先保留本轮约定，把差异列给导师判断。学生自己补充的备注放入论文交付文件夹，便于升级时保留。旧版个人工作区中的材料先核对归属和版本，不因升级自动搬动、覆盖或删除工程资料。

## 维护者开发与发布

当前处于本地开发阶段。只维护本开发目录，以 Git 提交保存每轮修改，变更汇总到 CHANGELOG 的“开发中”；不因日常修改生成分发 ZIP 或递增发布版本。VERSION 及模板内现有版本号保留为导入基线，开发完成后统一核对。

开发完成后统一上传 GitHub。发布前逐项核对根目录五个通用文件和三个通用目录中的文件，范围与 .gitignore 的允许清单一致，并检查入口、版本引用及模板修订状态；需要备用 ZIP 时在发布阶段再生成。新增通用文件时同步调整允许清单。

上述规则用于维护通用指导内容。学生对已确认交付物的打包流程，以及发布后克隆、拉取更新和 ZIP 备用的使用说明继续适用。

只发布通用规则、空白模板和虚构或已获准公开的示例。论文交付文件夹、真实论文、研究工程、数据、导师反馈以及原始对话均不属于指导包发布内容。学生收到的指导包应不依赖维护者电脑的路径。
